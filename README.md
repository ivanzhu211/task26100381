# pixelforge

PixelForge 感知指纹近重检索库：在上传新图片时，基于可信的 64 位感知指纹，
从内存索引中找出汉明距离不超过 8 的全部已有版本。不做图片解码，单工作区，
数据驻内存，调用方需串行访问。

## API

- `Upsert(versionID, fingerprint)`：登记版本；ID 已存在时替换指纹，旧指纹立即失效。
- `Remove(versionID)`：移除版本；移除不存在的 ID 是空操作。
- `Query(fingerprint) ([]Hit, int)`：返回距离 ≤8 的全部版本及精确距离，
  以及本次查询的完整 64 位距离求值次数。结果顺序不限。

## 运行

```sh
go test ./...                    # 全部测试（含规模测试）
go test -short ./...             # 跳过规模测试
go test -run TestScale -v .      # 单独运行规模测试，打印求值次数/内存/耗时
```

## 索引结构与维护

多索引哈希（MIH）。把 64 位指纹拆成低 32 位、高 32 位两个子串，各建一张
`map[uint32][]uint64` 哈希表（子串 → 版本 ID 列表），另有一张
`map[uint64]uint64` 保存每个版本的当前指纹。

- Upsert：若 ID 已存在，先按旧指纹从两张子串表中摘除，再按新指纹插入；
  单条更新只触碰两个桶，不重建索引。
- Remove：按当前指纹从两张表中摘除；桶变空即删除键，因此索引空间随当前
  记录数收缩，反复替换同一版本不会造成内存随修改次数增长。
- Query：对每个查询半串，枚举与其汉明距离 ≤4 的全部 32 位键
  （每半 1+32+496+4960+35960 = 41449 个，Gosper's hack 逐位组合生成），
  取两张表命中桶的并集作为候选，按版本 ID 去重后，对每个候选做一次完整
  64 位 popcount 距离求值（每次求值都计数），保留距离 ≤8 者。

## 为什么不会漏检

设查询 q 与某版本指纹 x 的汉明距离 d(q,x) ≤ 8。把距离拆到两个 32 位半串上：
d = d_lo + d_hi ≤ 8，由鸽巢原理 min(d_lo, d_hi) ≤ 4。因此 x 至少在一个半串上
与 q 的对应半串距离 ≤4，其键必被该半串的枚举覆盖，x 进入候选集并接受完整
距离求值。候选之外的版本两个半串距离都 ≥5，总距离 ≥10 > 8，本就不可能命中，
剪掉安全。最终只按完整 64 位精确距离放行，故无误报；候选按版本 ID 去重，故
无重复；同一指纹可挂在多个版本下，各自独立入桶、独立返回。相似性不具传递性，
索引不做任何基于"组"或"代表"的推断，只按上述充要条件筛选。

## 规模测试实测（固定种子 81，100 万互异均匀指纹，1000 次各翻 8 位的查询）

- 平均完整距离求值 ≈ 20 次/查询（上限 1 万），最大约 37 次。
- 峰值堆内存 ≈ 219 MiB（上限 768 MiB）。
- 构建约 0.6 s，查询平均约 3.5 ms（主要是 8.3 万个子串键枚举与哈希查找）。

理论期望：随机指纹某半串落入查询半串距离 ≤4 邻域的概率为 41449/2^32，
两个半串合计候选期望 ≈ 10^6 × 2 × 41449 / 2^32 ≈ 19.3，与实测一致。

## 最坏情况退化

枚举量与数据无关（固定 82898 个键/查询），但候选数取决于数据分布。若大量
指纹在某个半串上彼此距离 ≤4（极端情形：所有指纹相同或共享半个子串），对应
桶会容纳几乎全部记录，查询退化为对这些记录的完整扫描——结果仍然正确，只是
求值次数上升。规模限制（均值 ≤1 万）只针对均匀分布数据集；任何合法分布下
正确性性质始终成立。
